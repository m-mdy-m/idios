# IDIOS entity and relationship guide

This document defines the intended meaning of shared workspace records. It distinguishes stored facts from visual groupings so the UI, graph, API, TUI and future integrations use the same semantics.

## Primary relationships

| Entity | Owns or connects | Rules / meaning |
|---|---|---|
| Workspace profile | Workspace identity, focus, topics, website, bio and README | Workspace metadata, not a graph node. Do not infer identity or authorization from profile text. |
| Repository | Branches, issues, repository-scoped labels/milestones/settings | Repository references should resolve through the application/store before mutations. Deleting a repository must respect referential constraints and return a clear conflict if it still owns required records. |
| Branch | Repository, optional base branch, issues/completions that reference it | IDIOS tracks workflow branches; it does not create Git refs or perform a Git merge unless a future Git adapter explicitly implements that. |
| Issue | Repository, optional parent issue, dependencies, labels, milestone, optional branch, PR/completion lifecycle | Parent/sub-issue is a same-repository hierarchy and must be acyclic. `depends_on` means a prerequisite and may block starting/accepting work. |
| Pull request (IDIOS workflow record) | One issue, optional source/target branches, review/draft status, optional completion | This is a workflow/review record, not a hosted GitHub/GitLab PR. Accepting it records completion and transitions its issue atomically; it does not merge code. |
| Completion | Repository/branch, issue, accepted pull request, summary and sequence | Immutable-ish audit of completed workflow. Keep the cross-reference to the accepted PR and issue intact. |
| Project | Project-to-repository associations and project issues | Projects group work across repositories; the primary repository association is organizational, not a dependency. |
| Concept | Named reusable knowledge with a description and semantic relations | A concept link describes meaning/context. It does not automatically block issue progress. |
| Relation | Typed source entity + target entity + relation kind | The relation type is explicit. Use `depends_on` only for real blockers; prefer descriptive kinds such as `related_to` for informational links. Reject unknown entity types and empty endpoints. |
| Label | Global or repository-scoped classification; many-to-many issue assignments | Scope controls reuse; color is presentation data validated as a hex token. Labels categorize, they do not change workflow state. |
| Milestone | Repository- or project-scoped target date/description and issue assignments | The scope and owner must agree. A due date is a calendar date (`YYYY-MM-DD`) and is not a timestamp. |
| Note | Title, content, many reusable labels, optional links to other entities | Notes can have multiple labels. A note appears in the knowledge graph only when its link is marked `graph_visible`; otherwise it remains a normal note. |
| Quote | Text, author, source, optional source URL and category | A saved quote is a reading/reference item. Its source URL, when present, must be HTTP(S). No automatic graph edge is implied. |
| Scheduled job | Reminder/action + recurrence rule + next/last run metadata and optional branch | Jobs run local IDIOS actions. `interval`, `once`, `daily`, `weekly` and `monthly` have distinct required fields; one-time jobs must be in the future. A job does not become a graph node unless there is an explicit supported relationship. |
| Activity event | Recorded action with entity type/id and payload | Audit/history projection; normally read-only from the UI. It should link back to the entity it describes and should not be treated as a separate semantic relation. |
| Notification | Inbox message generated by an action/job | Notification state is independent of the underlying issue or job state; dismissing/reading a notification should not change the underlying entity. |
| Knowledge graph | Read-only projection of persisted entities and explicit relations | It must never be an alternate database or silently create relations. Layout positions are a local UI preference; graph data and relationship meaning come from the Engine. |

## Example workflow: a multi-repository project such as Gland

IDIOS can represent the planning and completion trail for a project that grows into several repositories:

1. Create a Project named `Gland`.
2. Link the main `gland` Repository and mark it as the project's primary repository. Link `emitter` and `events` as supporting repositories using their project association relationship metadata.
3. Create each Issue inside the Repository that owns the implementation. Add cross-repository issues to the Project when they contribute to the same larger plan. Use parent issues and explicit dependencies for decomposition and blockers.
4. Create a Branch for the Issue (for example, `feat/emitter-pipeline`) with the repository's `main` as its base. Each Repository has its own default `main` branch.
5. Create an IDIOS Pull Request that records the Issue, source branch, target branch (`main`), review notes and implementation summary. Accepting it creates a Completion record and completes the Issue in the IDIOS workflow.
6. Link a Note to the relevant Issue, Repository, Project or Concept and make it graph-visible. Use explicit semantic relations for ideas that connect across multiple entities; the graph is a projection of those saved relations.

Important current boundaries:

- Project-to-Repository membership is a group with one primary Repository; it is not yet a recursive repository tree. The `relationship` value can describe a child/module role, but there is no first-class parent-Repository field or validated nested path such as `gland/emitter` today.
- IDIOS Branches and Pull Requests are currently workflow metadata. Accepting a PR records completion and updates issue state; it does not create Git refs, modify a working tree or merge commits. A future Git adapter should execute those operations explicitly and report success/failure before marking a PR merged.
- Notes currently expose an optional direct entity link and multiple labels. Multi-target knowledge links should use explicit semantic relations or be added as a dedicated many-to-many note-relations feature rather than overloading the single direct link.

## Issue and PR lifecycle

```text
Open issue ── start (only when blockers are done) ──> In progress
    │                                                  │
    └── parent/sub-issue structure                      └── create draft/open IDIOS PR
                                                               │
                                           mark ready / close ─┤
                                                               └── accept
                                                                     │
                                completion record + issue transition <┘
```

The application layer is the authority for transitions. A page may disable a button for usability, but the server/application must repeat the rule because requests may originate from a different adapter or a stale UI.

## Knowledge graph nodes and edges

Current graph node families include repositories, branches, projects, issues, pull requests, completion records, concepts, labels, milestones, and linked notes explicitly marked graph-visible. Edges represent persisted membership/ownership, hierarchy, dependency, label/milestone assignment, PR/completion association, and explicit semantic relations. Keep edge labels human-readable and show a selected node’s description/status/reference in the inspector.

Labels and milestones are secondary nodes: hidden in the default canvas to reduce clutter, then exposed as a scoped subgraph while hovering a branch. Only entities that have a stored relationship to the branch's repository, its issues, or a linked project are revealed; the visual layer must not invent ownership edges. Repository, Issue, Pull Request, Project, Concept, Note, Branch, and Completion use distinct dimensions, shapes, and colors.

The graph's interaction model is intentionally separated:

- `lib/graph/layout.ts`: deterministic Organic and semantic-lane Flowchart starting layouts.
- `components/graph/GraphCanvas.tsx`: type-specific node sizes/shapes, interpolated position transitions between layout modes, animated relationship emphasis, pointer gestures, zoom/pan, branch-hover subgraphs and layout controls. Animations honor `prefers-reduced-motion`; dragging remains immediate to keep pointer tracking precise.
- `components/graph/GraphInspector.tsx`: selected entity details and neighbor navigation.
- `pages/GraphPage.tsx`: graph API loading, search/focus/depth and orchestration.
- `GET/PUT /api/graph/layout` and `POST /api/graph/layout/reset`: durable workspace graph presentation preferences stored in the local Engine SQLite database. Mode, each mode's node positions and each mode's viewport are stored separately; resetting one mode does not erase the other.

When adding node types, add a domain/store projection, its meaningful edges, a label/color in `lib/graph/constants.ts`, and a description/reference contract; then test that removing a filter or focusing a node does not invent or omit relationships unexpectedly.

## Settings and templates

Settings should be scoped to the object whose behavior they change:

- Workspace settings/preferences affect the local workspace as a whole.
- Repository settings affect repository workflow and defaults, not unrelated repositories.
- Issue fields (priority, due date, parent, branch, labels, milestone) belong to the issue workflow.
- Pull-request settings and future issue/PR templates should be reusable content/configuration, not special-case behavior inside one page. Resolve the applicable template when creating a record and preserve the rendered snapshot/explicit source if later edits must not rewrite historical records.
- Profile values describe the workspace and are user-entered metadata. Only use fields for visible profile features; do not treat them as permission grants or remote identity verification.

For any new setting, define its owner, valid values/defaults, migration behavior, and where it appears in web/TUI/CLI. For templates, define precedence (entity/repository default, then workspace default, then built-in fallback) and test empty/malformed templates before integrating them into create flows.
